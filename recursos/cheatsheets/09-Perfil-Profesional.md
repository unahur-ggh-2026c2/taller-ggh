# Cheatsheet — Perfil Profesional

> Referencia rápida para presentar proyectos y trabajo técnico mediante GitHub.

---

## Objetivo

El perfil profesional debe permitir identificar rápidamente:

```text
quién sos
   ↓
qué hacés
   ↓
qué sabés
   ↓
qué proyectos realizaste
   ↓
cómo trabajás
```

No se trata de mostrar cantidad.

Se trata de mostrar evidencia.

---

## Perfil de GitHub

Un perfil puede incluir:

```text
nombre
descripción
tecnologías
proyectos destacados
enlaces relevantes
actividad
README de perfil
```

Priorizá la información que ayude a comprender tu perfil profesional.

---

## README de perfil

Un README de perfil puede utilizarse como presentación.

Estructura posible:

```md
# Nombre

Descripción breve.

## Sobre mí

...

## Tecnologías

...

## Proyectos destacados

...

## Contacto

...
```

No es obligatorio utilizar todas las secciones.

---

## Presentar proyectos

Un proyecto destacado debería permitir comprender rápidamente:

```text
qué es
para qué sirve
qué tecnologías utiliza
cómo ejecutarlo
qué problema resuelve
```

Como mínimo:

```text
nombre
descripción
README
repositorio funcional
```

---

## README de proyecto

Una estructura posible:

```md
# Nombre del proyecto

Descripción breve.

## Objetivo

...

## Tecnologías

...

## Instalación

...

## Uso

...

## Ejemplo

...

## Estado

...

## Próximos pasos

...
```

Adaptala al proyecto.

---

## Elegir proyectos

No hace falta mostrar todos los repositorios.

Priorizá proyectos que demuestren:

```text
conocimientos
criterio
organización
documentación
capacidad de resolver problemas
```

Un proyecto pequeño pero bien presentado puede ser más útil que uno grande y desordenado.

---

## Evidencia

Un proyecto puede demostrar:

```text
código
   +
historial
   +
documentación
   +
Issues
   +
Pull Requests
   +
resultado
```

El repositorio debe permitir observar el trabajo realizado.

---

## Calidad antes que cantidad

Evitar pensar:

```text
"Necesito tener muchos repositorios."
```

Preferir:

```text
"Necesito que mis mejores proyectos estén bien presentados."
```

---

## Qué revisar antes de mostrar un repositorio

```text
[ ] Nombre claro.
[ ] Descripción clara.
[ ] README actualizado.
[ ] Instrucciones de instalación.
[ ] Ejemplo de uso.
[ ] Código ordenado.
[ ] Sin información sensible.
[ ] Historial razonable.
[ ] Estado del proyecto indicado.
```

---

## Descripción breve

Una buena descripción responde rápidamente:

```text
¿Qué es?
¿Para qué sirve?
```

Ejemplo:

```text
Aplicación de consola para gestionar tareas
utilizando Python y persistencia en archivos.
```

Evitar:

```text
Mi proyecto final
Trabajo de programación
Aplicación
```

---

## Estado del proyecto

Indicá claramente si el proyecto está:

```text
En desarrollo
Activo
Completado
Mantenimiento
Archivado
```

No presentes como terminado algo que todavía está en desarrollo.

---

## Tecnologías

Podés indicar las tecnologías principales:

```text
Python
Git
GitHub
Markdown
```

No es necesario listar cada herramienta utilizada.

Priorizá las que sean relevantes para comprender el proyecto.

---

## Documentación como evidencia

Una buena documentación permite que otra persona:

```text
lea
 ↓
instale
 ↓
ejecute
 ↓
comprenda
```

Si el proyecto requiere explicaciones que solamente vos podés proporcionar, todavía hay trabajo de documentación por hacer.

---

## Proyecto reproducible

Antes de presentar un proyecto, probá seguir sus propias instrucciones.

```text
README
  ↓
instalación
  ↓
ejecución
  ↓
resultado
```

Si las instrucciones no permiten reproducir el proyecto, actualizá el README.

---

## Seguridad

Antes de hacer público un repositorio:

```text
[ ] No hay contraseñas.
[ ] No hay tokens.
[ ] No hay claves.
[ ] No hay credenciales.
[ ] No hay datos sensibles.
[ ] `.gitignore` fue revisado.
```

Importante:

> Publicar un secreto y eliminarlo después del archivo no significa necesariamente que haya desaparecido del historial.

---

## Actividad

La actividad de GitHub puede mostrar:

```text
commits
Issues
Pull Requests
repositorios
colaboración
```

No busques generar actividad artificial.

La actividad debe surgir del trabajo real.

---

## Colaboración como evidencia

Las Pull Requests pueden mostrar capacidad para:

```text
trabajar con ramas
proponer cambios
recibir feedback
corregir
revisar
integrar
```

Esto puede ser más significativo que mostrar solamente commits.

---

## Presentación profesional

Antes de compartir tu perfil:

```text
perfil
  ↓
repositorios destacados
  ↓
README
  ↓
proyectos
  ↓
documentación
```

Preguntate:

> ¿Qué impresión obtiene alguien que ve mi perfil por primera vez?

---

## Checklist del perfil

```text
[ ] El perfil tiene una presentación clara.
[ ] Los proyectos destacados son relevantes.
[ ] Los README están actualizados.
[ ] Los repositorios públicos fueron revisados.
[ ] No hay información sensible.
[ ] Los proyectos pueden comprenderse sin explicación oral.
[ ] Los enlaces funcionan.
[ ] La información representa mi situación actual.
```

---

## Comandos útiles

Para revisar el estado:

```bash
git status
```

Para revisar historial:

```bash
git log --oneline --graph --all
```

Para revisar el último commit:

```bash
git show HEAD
```

Para comprobar archivos ignorados:

```bash
git check-ignore -v archivo
```

---

## Proyecto + perfil

La relación puede pensarse así:

```text
proyecto
   ↓
repositorio
   ↓
documentación
   ↓
historial
   ↓
resultado
   ↓
perfil profesional
```

El perfil no debería inventar una experiencia.

Debe presentar de manera clara la experiencia que realmente existe.

---

## Regla práctica

Antes de compartir un proyecto, asegurate de que otra persona pueda responder:

```text
¿Qué es?
¿Para qué sirve?
¿Cómo lo ejecuto?
¿Qué tecnologías utiliza?
¿Qué demuestra?
```

> **Un perfil profesional no se construye solamente mostrando lo que sabés: se construye mostrando evidencia de cómo trabajás.**

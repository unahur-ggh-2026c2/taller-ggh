# Módulo 09 — Proyecto Final

> **Llegó el momento de dejar de practicar Git por separado y utilizarlo para construir, organizar y presentar un proyecto completo.**

---

## ¿Qué vamos a hacer?

Durante el curso aprendimos progresivamente a trabajar con Git y GitHub:

```text
comprender Git
     ↓
crear repositorios
     ↓
registrar cambios
     ↓
analizar historial
     ↓
trabajar con GitHub
     ↓
documentar con Markdown
     ↓
trabajar con ramas
     ↓
colaborar
     ↓
construir un perfil profesional
```

Ahora vamos a integrar todo ese recorrido.

El Proyecto Final propone trabajar sobre un proyecto real y aplicar, de manera consciente, las herramientas y prácticas aprendidas durante el curso.

---

# ¿Por qué un proyecto final?

Porque conocer comandos por separado no alcanza.

Queremos comprobar que podés utilizarlos dentro de un proceso completo.

El objetivo no es demostrar:

```text
"sé muchos comandos de Git"
```

sino:

```text
"sé utilizar Git y GitHub para trabajar sobre un proyecto."
```

---

# ¿Qué se espera?

El proyecto debe permitir observar:

```text
planificación
     ↓
organización
     ↓
desarrollo
     ↓
versionado
     ↓
documentación
     ↓
colaboración
     ↓
revisión
     ↓
integración
     ↓
presentación
```

No todas las etapas tendrán necesariamente la misma complejidad.

Lo importante es que exista un proceso claro y que puedas explicar las decisiones tomadas.

---

# Proyecto real

El proyecto puede ser:

- un programa;
- una aplicación;
- una herramienta;
- un proyecto académico;
- un proyecto personal;
- material educativo;
- documentación técnica;
- otro trabajo acordado con el docente.

No se evalúa solamente el producto final.

Se evalúa también:

```text
cómo fue construido
```

y:

```text
cómo fue organizado y documentado.
```

---

# Modalidad

El proyecto puede realizarse:

### Individual

Una persona desarrolla el proyecto y aplica el flujo completo de trabajo.

### En equipo

Dos o más personas trabajan sobre un mismo repositorio utilizando Git y GitHub como herramientas de colaboración.

La modalidad será definida por el docente.

---

# Objetivo general

Integrar los conocimientos desarrollados durante el curso mediante la planificación, desarrollo, documentación, versionado, colaboración y presentación de un proyecto utilizando Git y GitHub.

---

# Objetivos específicos

Al finalizar el proyecto deberías poder:

- crear y organizar un repositorio;
- definir tareas;
- utilizar Issues;
- trabajar con ramas;
- registrar cambios mediante commits;
- sincronizar repositorios;
- utilizar Pull Requests;
- realizar revisiones;
- resolver conflictos;
- documentar el proyecto;
- aplicar `.gitignore`;
- mantener una historia comprensible;
- presentar el resultado;
- explicar las decisiones tomadas.

---

# El proceso importa

Un proyecto puede funcionar y aun así presentar un proceso deficiente.

Por ejemplo:

```text
todo sobre main
```

o:

```text
un único commit
```

o:

```text
README inexistente
```

o:

```text
sin revisión
```

o:

```text
sin documentación
```

El Proyecto Final busca evitar ese enfoque.

El resultado debe ser:

```text
producto
+
proceso
+
evidencia
```

# Estructura del módulo

Este módulo contiene:

```text
README.md
00-Guia-Docente.md
01-Practica.md
02-Ejercicios.md
03-Desafios.md
04-Proyecto.md
05-Recursos.md
```

El `README.md` presenta el módulo.

La guía docente establece el enfoque pedagógico.

La práctica permite preparar el proyecto.

Los ejercicios permiten consolidar conocimientos.

Los desafíos permiten profundizar.

El proyecto define la entrega final.

Los recursos permiten continuar consultando y aprendiendo.

# Producto final

Al finalizar debería existir un repositorio que pueda ser comprendido por otra persona.

Como mínimo debería incluir:

```text
README.md
.gitignore
código o material del proyecto
```

Cuando corresponda, también:

```text
docs/
tests/
CONTRIBUTING.md
LICENSE
```

La estructura concreta dependerá del proyecto.

---

# Documentación

El proyecto debe explicar:

```text
qué es
para qué sirve
cómo instalarlo
cómo utilizarlo
qué tecnologías utiliza
```

La documentación debe coincidir con el estado real del proyecto.

---

# Git como parte del proyecto

Git no debe aparecer solamente como requisito administrativo.

Debe utilizarse realmente durante el desarrollo.

Debería existir evidencia de:

```text
commits
ramas
historial
integraciones
```

Cuando el proyecto sea colaborativo, también:

```text
Issues
Pull Requests
revisiones
```

---

# GitHub como espacio de trabajo

GitHub será utilizado como parte del proceso.

No solamente como lugar donde "subir el proyecto".

Debe permitir observar:

```text
organización
seguimiento
propuestas
revisión
colaboración
```

---

# Perfil profesional

El proyecto final también puede convertirse en una pieza de portafolio.

Por eso debería ser:

```text
comprensible
documentado
organizado
honesto
presentable
```

No es necesario que sea un proyecto profesional comercial.

Debe ser una representación real de tu trabajo y de lo aprendido durante el curso.

---

# Honestidad técnica

No es necesario aparentar un nivel que todavía no tenés.

El proyecto debe permitir decir:

```text
Esto hice.
```

```text
Esto aprendí.
```

```text
Esto todavía necesito mejorar.
```

La capacidad de reconocer limitaciones también forma parte de una práctica profesional saludable.

---

# Seguridad

Antes de publicar el repositorio se debe verificar que no contenga:

```text
contraseñas
tokens
claves
credenciales
datos personales innecesarios
información confidencial
```

El archivo:

```text
.gitignore
```

debe utilizarse cuando corresponda.

Recordá:

> `.gitignore` evita determinados archivos del seguimiento futuro; no elimina automáticamente información que ya haya sido registrada en Git.

---

# Presentación final

El proyecto deberá ser presentado.

La presentación debería permitir explicar:

```text
qué problema se buscó resolver
qué se construyó
cómo se organizó el trabajo
qué tecnologías se utilizaron
cómo se utilizó Git
cómo se utilizó GitHub
qué dificultades aparecieron
cómo se resolvieron
qué se aprendió
```

---

# Defensa

Durante la presentación pueden realizarse preguntas sobre:

- decisiones;
- comandos;
- ramas;
- commits;
- GitHub;
- documentación;
- conflictos;
- organización;
- problemas encontrados.

No alcanza con mostrar el proyecto.

Hay que poder explicar el proceso.

---

# Evaluación

La evaluación tendrá en cuenta:

## Proyecto

- claridad;
- organización;
- coherencia;
- resultado.

## Git

- utilización correcta;
- commits;
- ramas;
- historial.

## GitHub

- repositorio;
- Issues;
- Pull Requests;
- revisiones;
- integración.

## Documentación

- README;
- instrucciones;
- ejemplos;
- claridad.

## Seguridad

- `.gitignore`;

- criterio de publicación.

## Presentación

- comprensión;
- comunicación;
- capacidad para justificar decisiones.

---

# No se evalúa solamente el resultado

El proyecto final no se reduce a:

```text
¿funciona?
```

También importa:

```text
¿se entiende?
¿está documentado?
¿tiene una historia?
¿se puede mantener?
¿se puede explicar?
¿se puede revisar?
```

---

# Criterio general

El Proyecto Final debe mostrar una evolución respecto de los primeros módulos.

Al comienzo:

```text
"Quiero aprender Git."
```

Al final:

```text
"Utilizo Git para trabajar sobre proyectos de manera organizada."
```

Ese es el cambio que buscamos.

---

# Cierre del curso

Este proyecto representa el cierre del recorrido inicial.

No significa que hayas terminado de aprender Git.

Git y GitHub tienen muchas funcionalidades que quedan fuera del curso.

Significa que ya disponés de una base para continuar aprendiendo de manera autónoma.

```text
aprender
   ↓
practicar
   ↓
construir
   ↓
documentar
   ↓
colaborar
   ↓
revisar
   ↓
mejorar
```

Ese ciclo puede continuar indefinidamente.

> **El objetivo final no es saber Git. Es poder trabajar mejor gracias a Git.**

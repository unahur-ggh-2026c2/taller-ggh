# Módulo 08 — Perfil Profesional

> **Git no solamente registra cómo evoluciona un proyecto. También puede convertirse en evidencia de cómo trabajás.**

---

## ¿Qué vamos a aprender?

Hasta ahora aprendimos a utilizar Git y GitHub para:

```text
crear repositorios
     ↓
registrar cambios
     ↓
trabajar con ramas
     ↓
colaborar
     ↓
revisar cambios
     ↓
integrar trabajo
```

Ahora vamos a cambiar ligeramente la perspectiva.

Hasta este punto, GitHub fue principalmente:

```text
una herramienta para trabajar sobre proyectos
```

En este módulo vamos a comenzar a utilizarlo también como:

```text
una representación pública de nuestro trabajo técnico
```

La pregunta deja de ser solamente:

> ¿Cómo trabajo con Git?

y comienza a aparecer otra:

> ¿Qué puede mostrar mi repositorio sobre mi forma de trabajar?

---

# ¿Qué entendemos por perfil profesional?

Un perfil profesional no es solamente una foto, un currículum o una lista de tecnologías.

En el ámbito del desarrollo de software también puede estar construido a partir de:

- proyectos;
- documentación;
- código;
- historial de cambios;
- contribuciones;
- Pull Requests;
- Issues;
- decisiones técnicas;
- capacidad de explicar lo realizado.

Podemos representarlo como:

```text
Perfil profesional
        ↓
    experiencia
        +
    proyectos
        +
 documentación
        +
  contribuciones
        +
 comunicación
```

GitHub puede ser una parte de esa evidencia.

---

# GitHub como evidencia

Un repositorio puede mostrar mucho más que los archivos actuales.

También puede mostrar:

```text
qué se hizo
cuándo se hizo
cómo evolucionó
qué problemas aparecieron
cómo se resolvieron
cómo se colaboró
```

Por eso el historial que trabajamos durante los módulos anteriores adquiere ahora otra importancia.

```text
historial técnico
       ↓
evidencia del proceso
```

---

# No se trata de aparentar

El objetivo de este módulo no es construir un perfil artificial.

No buscamos:

```text
tener muchos repositorios vacíos
```

ni:

```text
generar actividad solamente para que aparezca actividad.
```

Buscamos construir evidencia real de aprendizaje y trabajo.

Es preferible tener:

```text
3 proyectos bien documentados
```

que:

```text
30 repositorios sin contexto.
```

---

# El repositorio como presentación

Un repositorio puede funcionar como una pequeña presentación técnica.

Una persona que lo visite debería poder comprender rápidamente:

```text
¿Qué es?
¿Por qué existe?
¿Cómo se utiliza?
¿Cómo está organizado?
¿Qué aprendí?
¿Cómo puedo probarlo?
```

Por eso el `README.md` adquiere un papel fundamental.

---

# README como puerta de entrada

Un buen `README.md` debería permitir que alguien nuevo pueda orientarse rápidamente.

Puede incluir:

```text
nombre del proyecto
descripción
objetivo
características
instalación
uso
ejemplos
estructura
contribución
licencia
```

No todos los proyectos necesitan todas las secciones.

La documentación debe estar relacionada con el proyecto real.

---

# Perfil de GitHub

El perfil de GitHub puede reunir información sobre nuestro trabajo.

Puede incluir:

- presentación personal;
- intereses técnicos;
- proyectos destacados;
- tecnologías;
- enlaces relevantes;
- información de contacto profesional.

El objetivo es facilitar que otra persona comprenda:

```text
quién soy
qué hago
qué me interesa
qué puedo mostrar
```

---

# Perfil técnico

Un perfil técnico no debería convertirse en una lista interminable de tecnologías.

No se trata de escribir:

```text
Python
Java
JavaScript
C
C++
SQL
Docker
Kubernetes
AWS
Git
...
```

si después no existe evidencia de haber trabajado con ellas.

Es más útil poder mostrar:

```text
Tecnología
   ↓
proyecto
   ↓
uso concreto
   ↓
resultado
```

---

# Proyectos destacados

Un perfil profesional debería priorizar proyectos que permitan demostrar capacidades.

Un proyecto puede mostrar:

- resolución de problemas;
- programación;
- documentación;
- organización;
- pruebas;
- control de versiones;
- trabajo colaborativo.

No es necesario que sea un proyecto enorme.

Un proyecto pequeño, pero bien resuelto y explicado, puede resultar mucho más útil.

---

# Qué debería mostrar un proyecto

Al observar un proyecto, otra persona debería poder encontrar:

```text
README
   ↓
objetivo
   ↓
instalación
   ↓
uso
   ↓
ejemplos
   ↓
estructura
```

Y, cuando corresponda:

```text
tests
documentación
Issues
Pull Requests
historial
```

---

# La historia también importa

Durante el curso aprendimos a observar:

```bash
git log --oneline --graph --all
```

Ahora podemos interpretar esa historia de otra manera.

No solamente muestra:

> cómo evolucionó el proyecto.

También puede mostrar:

> cómo trabajó la persona que lo desarrolló.

Una historia razonablemente organizada transmite:

- cuidado;
- criterio;
- capacidad de evolución;
- comprensión de Git.

---

# Commits como evidencia

Un commit debería comunicar una modificación concreta.

Compará:

```text
cambios
```

con:

```text
Agrega validación de entrada
```

El segundo mensaje aporta información.

Los commits forman parte de la historia técnica del proyecto.

---

# Issues como evidencia

Las Issues también pueden mostrar cómo se organiza el trabajo.

Una Issue bien planteada puede mostrar:

```text
problema
 ↓
análisis
 ↓
objetivo
 ↓
solución
```

Esto permite observar capacidad para transformar una necesidad en una tarea concreta.

---

# Pull Requests como evidencia

Las Pull Requests pueden mostrar:

- qué cambios se propusieron;
- por qué se realizaron;
- cómo fueron revisados;
- qué observaciones recibieron;
- cómo se corrigieron;
- cómo fueron integrados.

Por eso el trabajo colaborativo desarrollado en el módulo anterior también forma parte de nuestro perfil técnico.

---

# Documentación como competencia profesional

Un desarrollador no solamente escribe código.

También necesita poder explicar:

```text
qué hizo
por qué lo hizo
cómo utilizarlo
cómo modificarlo
```

Por eso la documentación es una competencia técnica.

Un proyecto difícil de entender puede transmitir una imagen muy diferente a un proyecto técnicamente equivalente pero bien documentado.

---

# Markdown

Markdown será una herramienta importante para construir documentación técnica.

Ya trabajamos:

- títulos;
- listas;
- enlaces;
- tablas;
- código;
- estructura documental.

Ahora vamos a aplicar esos conocimientos a materiales que forman parte de un proyecto que puede ser presentado profesionalmente.

---

# Portafolio

Un portafolio es una selección organizada de trabajos que permite mostrar capacidades.

Puede incluir:

```text
proyectos personales
proyectos académicos
contribuciones
ejemplos técnicos
documentación
```

No es necesario que todos sean proyectos comerciales.

Lo importante es que permitan demostrar lo que sabemos hacer.

---

# Proyecto académico como evidencia

Un proyecto realizado durante una carrera o curso puede convertirse en una pieza de portafolio.

Pero no alcanza con subirlo.

Conviene agregar contexto:

```text
¿Qué problema resolvía?
¿Qué aprendí?
¿Qué tecnologías utilicé?
¿Qué decisiones tomé?
¿Qué dificultades encontré?
¿Qué mejoraría?
```

Esto transforma:

```text
trabajo práctico
```

en:

```text
evidencia de aprendizaje.
```

---

# Presentar un proyecto

Una presentación técnica efectiva debería poder responder:

### Problema

¿Qué problema se buscaba resolver?

### Solución

¿Qué se construyó?

### Tecnologías

¿Qué herramientas se utilizaron?

### Decisiones

¿Qué decisiones técnicas fueron importantes?

### Resultado

¿Qué se consiguió?

### Aprendizaje

¿Qué se aprendió durante el proceso?

---

# Capturas y demostraciones

Cuando sea útil, un proyecto puede incluir:

- capturas;
- GIFs;
- diagramas;
- ejemplos;
- videos;
- demostraciones.

Pero deben utilizarse para explicar el proyecto.

No deben reemplazar una documentación clara.

---

# Perfil y privacidad

No toda información personal debe hacerse pública.

Un perfil profesional debe compartir solamente la información que resulte apropiada.

Hay que diferenciar:

```text
información profesional
```

de:

```text
información personal innecesaria.
```

La construcción de un perfil profesional también implica aprender a gestionar qué información hacemos pública.

---

# Repositorios públicos y privados

No todos los proyectos tienen que ser públicos.

Un repositorio puede contener información:

- académica;
- personal;
- profesional;
- sensible;
- confidencial.

Antes de publicar un proyecto debemos verificar qué contiene.

Especialmente:

```text
contraseñas
tokens
claves
credenciales
datos personales
configuraciones sensibles
```

Nunca deberían incorporarse al repositorio.

---

# Seguridad

Una regla fundamental:

> **Nunca publiques secretos en un repositorio.**

Por ejemplo:

```text
API_KEY=...
PASSWORD=...
TOKEN=...
SECRET=...
```

El control de versiones registra la historia.

Por lo tanto, eliminar un secreto del archivo actual no necesariamente significa que haya desaparecido de la historia.

Este tema será trabajado de manera práctica.

---

# `.gitignore`

El archivo:

```text
.gitignore
```

permite indicar archivos y directorios que Git no debería incorporar al seguimiento.

Puede utilizarse para evitar publicar:

- archivos temporales;
- configuraciones locales;
- entornos virtuales;
- archivos generados;
- secretos almacenados localmente.

No debe entenderse como un mecanismo de seguridad para secretos que ya fueron publicados.

---

# Identidad profesional

El perfil profesional también se construye mediante la forma de comunicar.

Un buen perfil debería transmitir:

```text
claridad
coherencia
honestidad
criterio técnico
capacidad de aprendizaje
```

No es necesario aparentar saber todo.

Es mucho más valioso poder mostrar:

> "Esto aprendí, esto construí y esto puedo explicar."

---

# CV y GitHub

GitHub y el currículum cumplen funciones diferentes.

El CV resume:

```text
experiencia
formación
habilidades
```

GitHub puede aportar:

```text
evidencia
proyectos
historial
contribuciones
```

Pueden complementarse.

```text
CV
 ↓
qué hice

GitHub
 ↓
evidencia de cómo trabajo
```

---

# LinkedIn y otros perfiles

El perfil profesional puede extenderse a otras plataformas.

Por ejemplo:

```text
CV
GitHub
LinkedIn
sitio personal
portafolio
```

No es necesario tener presencia en todas.

Lo importante es que exista coherencia entre los distintos espacios.

---

# Coherencia profesional

Si una persona presenta:

```text
CV → Python
GitHub → proyectos Python
Portafolio → proyectos Python
```

existe una narrativa coherente.

Si cada espacio muestra algo completamente diferente, puede resultar más difícil comprender el perfil.

---

# No medir el valor por cantidad

No es necesario perseguir:

```text
muchos commits
muchos repositorios
muchas estrellas
muchos seguidores
```

La cantidad no reemplaza la calidad.

Un perfil profesional sólido puede construirse lentamente.

```text
proyecto
 ↓
documentación
 ↓
mejora
 ↓
aprendizaje
 ↓
nuevo proyecto
```

---

# Construcción progresiva

El perfil profesional no se termina en este módulo.

Puede evolucionar:

```text
aprendizaje
   ↓
proyectos
   ↓
experiencia
   ↓
contribuciones
   ↓
mejora continua
```

Por eso este módulo debe entenderse como un punto de partida.

---

- relacionar conocimientos con evidencia concreta.

Y, sobre todo:

> **deberías poder mostrar lo que aprendiste sin depender exclusivamente de decir que lo aprendiste.**

# Idea central

Un perfil profesional técnico no debería responder solamente:

```text
"¿Qué tecnologías conozco?"
```

También debería permitir responder:

```text
¿Qué construí?
¿Cómo trabajo?
¿Cómo resuelvo problemas?
¿Cómo documento?
¿Cómo colaboro?
¿Qué puedo explicar?
¿Qué sigo aprendiendo?
```

Git y GitHub pueden ayudar a construir esa evidencia.

Pero el objetivo no es construir una fachada.

Es construir, poco a poco, una trayectoria técnica que pueda ser observada.

> **Tu perfil profesional no debería decir solamente lo que sabés hacer. Debería mostrarlo.**
